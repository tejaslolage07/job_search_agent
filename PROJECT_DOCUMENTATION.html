job_search_agent

Monitors specific companies' public career pages, detects new job listings, and ranks them against your profile — newest first. Discovery and matching only: it never applies, logs in, or sends messages.

1. The big picture

One pass of the tool does two independent jobs. Crawling (run) is fully deterministic: it fetches each company's jobs, compares them with what is stored, and records what is new, changed, or gone. Matching (match) scores stored jobs against your profile and prints a ranked list. Keeping them separate means crawling never needs your resume, and matching never touches the network.

3. Discovery: how jobs are fetched

For each active company, in order:

  1. Detect the ATS when ats_type is auto. The careers URL is matched against known patterns (e.g. jobs.lever.co/<token>); if that fails, the page HTML is scanned for embedded board links. The result is saved so later runs skip detection.
  2. Public JSON feeds for Greenhouse, Lever and Ashby (never HTML scraping). Endpoints were verified against live boards: 
    Greenhouse  GET boards-api.greenhouse.io/v1/boards/{token}/jobs?content=true
Lever       GET api.lever.co/v0/postings/{token}?mode=json
Ashby       GET api.ashbyhq.com/posting-api/job-board/{token}?includeCompensation=true
  3. Workday: the public CXS endpoint the career site itself calls. List pages give only title/location, so details are fetched just for jobs not seen before (capped per run).
  4. Custom sites, trying in this order and stopping at the first that returns jobs: JSON-LD JobPosting on the page → sitemap job URLs (each fetched, capped) → per-company CSS selectors from config/selectors.yaml.
  5. Playwright (headless browser) only if a custom page has needs_js: true and nothing above worked. Each fallback is logged and shown in status as an expensive fallback.

Each source normalises its output into the same RawJob shape (title, url, external id, location, posted date, description text, workplace type, salary text, raw payload), so everything after discovery is source-agnostic. Greenhouse's escaped HTML, Lever's epoch-millisecond dates, and Ashby's compensation summaries are all handled in the adapters.

4. Politeness and safety rules

  • Public endpoints only. No login, no LinkedIn/Naukri.
  • robots.txt is fetched once per host and respected. A 4xx robots file means "no restrictions" (RFC 9309); a 5xx means "assume disallowed".
  • Honest User-Agent: job_search_agent/0.1 (personal job-discovery tool; honours robots.txt).
  • Rate limit: at most 1 request per second per host.
  • Retries with exponential backoff on 5xx and network errors. Redirect loops are not retried.
  • Stop, don't evade: the second 403/429 from a host marks it blocked for the rest of the run; no further requests go to it.
  • One failure never spreads: an error in one company is logged and the crawl continues with the rest.

6. How "new / changed / removed" is decided

OutcomeRule
NewIdentity not in the database. A job that was removed and reappears is re-activated and logged as new (reappeared).
ChangedTitle, location, or description hash differs from the stored row. The event lists which fields changed.
RemovedMissing from 2 consecutive successful fetches of its company (missed_count reaches 2). Seen again → counter resets.
DuplicatesSame identity twice in one fetch collapses to one.

A failed fetch never removes anything. Failures raise before the diff is computed. As an extra guard, a feed that returns zero jobs while jobs are stored is treated as a failure, not as "everything was removed".

Idempotency: with no site changes, a second run reports zero new, changed, and removed jobs. --dry-run fetches and diffs and prints the result, but writes no jobs, events, or runs (it still syncs the companies table from the CSV).

7. Matching: two AI phases (no rules)

Phase 1: job + profile details

Prompt: config/llm_prompt.md. The model gets the job (title, company, location, description) and the profile details built by Profile.details_text(): years of experience, target titles, seniority range, max years the job may ask for, preferred locations and hybrid / onsite rules, must-have and nice-to-have skills, dealbreaker words, companies to avoid, and your current and expected CTC with the USD rate. The job's posted pay is sent as its own field, so the model can reject jobs whose pay is clearly below your expected minimum (pay that is not stated is neutral). It answers one line: match: <word>, no match: <word> or ambiguous, where the word is the strongest parameter behind the verdict.

Phase 2: job + resume, only when phase 1 says ambiguous

  • Prompt: config/llm_prompt_resume.md. The resume goes in place of the profile details. Ambiguous is not allowed: the prompt forbids it and the reply parser rejects it, so a phase-2 job ends as match or no match (an off-spec or ambiguous reply is a failed check that is retried next run, never a result).
  • Resume PDFs are parsed with pypdf, cached by file hash, and only sent in phase 2. With several resume variants, one match is enough; all must say no match to reject.
  • If the key is missing, the API fails, the reply is off-spec or the resume cannot be read, the job stays in review (shown as "Not checked") with method llm-failed and is asked again on the next run. There is no non-AI fallback.

What is sent: the job text and posted pay, the profile details above (pay included) in phase 1, and the resume text in phase 2. Notice period, work authorization and resume file paths are never sent. Model, effort, retries, concurrency, caching: the llm: section of config/matching.yaml (OPENAI_MODEL in .env overrides the model).

Cost design: reasoning effort is none for phase 1 (quick triage, about 6 output tokens per call) and low for phase 2 (resume_reasoning_effort, the careful resume check). With cache: explicit only the shared start of each prompt (instructions + profile in phase 1, instructions + resume in phase 2, ended by the {{cache_here}} line of the prompt file) is cached and read back at about a tenth of the input price; the per-job text after it is billed as plain input. The shared start must reach about 1,024 tokens or nothing is cached, which is why the phase-1 prompt carries worked examples. Every API call is stored in the llm_calls table (full request and response, input / output / reasoning / cached / cache-write tokens).

Audit proof: match_results.resume_hash is NULL whenever phase 2 did not run. If it is set, the resume was sent; if it is NULL, it was not. explain JOB_ID shows each call's verdict, word, model and token counts.

When jobs are re-scored

A job is asked again only if its content hash (title, location, description, salary text), the profile details the AI sees (pay included), or the prompt / model fingerprint changed — or you pass --rescore. Notice period and work authorization are never sent, so changing them re-scores nothing. Failed checks are retried automatically. Jobs are judged llm.concurrency (8) at a time and each result is saved as it arrives, so an interrupted run keeps what it finished.

8. Ranking (and time zone)

Time zone: every time is Indian Standard Time (IST, UTC+05:30, no daylight saving). Stored timestamps look like 2026-11-21T00:09:29+05:30, so they all share one offset and sort correctly as text. Times that arrive in another zone (an ATS's …Z UTC timestamp, an epoch number) are converted on the way in; LinkedIn only gives a date, which is kept as that IST day at 00:00. "Calendar days" (the Posted filter, today / yesterday ages) are IST days, schedules run on IST, and the dashboard displays IST whatever the browser's zone. A database written before this change is converted once, automatically, on the next start, after a backup copy (job_search_agent.db.before-ist.bak). Code: src/job_search_agent/timeutil.py.

Sort key: calendar day of posted_at (falling back to first_seen_at) descending → final_score descending → exact timestamp descending. Score can reorder jobs within a day but can never lift an older day's job above a newer one.

11. The company catalog (separate from the crawler)

config/india_companies.csv is a reference list of India-based software employers (about 1,200 rows), banded Large / Medium / Small / Micro. It is not crawled directly; its first seven columns match companies.csv so chosen rows can be copied across and set active=true. Every row starts active=false.

  • Where it came from: names recalled from memory, plus companies from India_Software_Hiring_Companies_v2.xlsx (Inc42 / Seedtable lists). Size bands are approximate. Old rows use one band scheme and xlsx-sourced rows another; the size_basis column says which.
  • Verified (verified=yes) means a live public Greenhouse/Lever/Ashby board was found. Only a small fraction qualify, because most large Indian employers use Workday, SuccessFactors, or their own sites.
  • portal_status records the link check: ok, dead, blocked (401/403), robots disallowed, or unreachable. fallback_portal is a LinkedIn search link for browsing by hand; the tool never crawls it.
  • Scripts: scripts/build_catalog.py (probe ATS boards, write CSV; resumable), scripts/check_portals.py (check xlsx portals), scripts/merge_xlsx.py (append missing companies).

12. Tests

Pytest tests with no live network (saved fixtures, httpx.MockTransport, and a fake OpenAI server). They cover: new / changed / removed-after-2-runs, failed fetch not removing, duplicates, the two-phase matcher (phase 1 never sends the resume, an ambiguous phase-1 answer goes to phase 2, phase 2 can never end ambiguous, failures are retried), what is and is not sent in each request body, concurrency, caching and cancelling, the dashboard API and the test kit.
